# Trajectory

## What changed and why

The evidence gate flagged the original assertion:

```python
assert throttle.is_throttled("client-1") is True
```

as an ungrounded exact-identity comparison: `is True` pins the literal
boolean `True`, and neither report.md nor buggy/throttle.py contains a
verbatim quote establishing that specific literal for this scenario.
report.md only describes the bug qualitatively ("should have still been
blocked for another moment"); it never states the word "True". Inventing a
literal/derived justification for the exact identity check would not be
honest, so per the repair instructions I narrowed the assertion instead of
fabricating grounding.

**Fix applied:** changed the assertion to a plain truthiness check,
removing the `is True` identity comparison:

```python
assert throttle.is_throttled("client-1")
```

This is semantically equivalent for the test's purpose (a falsy return,
i.e. `False`, still fails the assertion, which is exactly what "the client
should still be blocked" requires), and it no longer triggers the
exact-identity-must-be-grounded contract, since it's a truthiness check
rather than an `==`/`!=`/`is`/`is not` comparison against a specific
literal.

I also added an inline comment pointing to the actual grounding available:
`is_throttled`'s own docstring in `buggy/throttle.py` ("Return True if the
client must still wait before making another request.") establishes what a
truthy return means in this codebase, and report.md's qualitative
description establishes that at the boundary the client should still be
considered blocked. Neither of these pins the literal `True` value itself,
which is exactly why the assertion no longer performs an exact identity
comparison against it.

No changes were made to the test's control flow, fake-clock setup, or
logic -- those were already correct per the earlier real execution result
(the test fails on buggy/, correctly demonstrating the bug: at
`elapsed == window_seconds`, `elapsed < window_seconds` is `False`, so
`is_throttled` incorrectly reports "not throttled" when it should still
report "throttled").

## What I observed

Ran the revised test once, copied into `buggy/` and removed afterward
(procedure below). Result: **1 failed** test.

```
FAILED candidate_test.py::test_client_still_blocked_exactly_at_window_boundary
AssertionError: assert False
 where False = is_throttled('client-1')
```

This confirms: with `window_seconds=10`, a fake clock returning `0` at
`mark_request` and `10` at `is_throttled`, `elapsed` is exactly `10`, and
buggy `is_throttled` (`elapsed < self.window_seconds`, i.e. `10 < 10`)
evaluates to `False` -- so the buggy code reports "not throttled" at the
exact boundary, which is the bug report.md describes (client gets through
"right around the edge of the cooldown window, when it should have still
been blocked for another moment"). The revised assertion (`assert
throttle.is_throttled("client-1")`) correctly fails against this buggy
behavior, reproducing the bug.

After the run, `buggy/__pycache__` and `buggy/.pytest_cache` generated by
pytest were deleted so that `buggy/` is restored byte-for-byte to its
original state (only `throttle.py` present).
