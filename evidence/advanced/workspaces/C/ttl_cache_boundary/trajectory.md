# Trajectory

## What I read

- `report.md`: describes intermittent support reports where a client was
  able to repeat an action "right around the edge of the cooldown window,
  when it should have still been blocked for another moment." Described as
  hard to reproduce by hand / intermittent, but happening often enough to
  not be a fluke.
- `buggy/throttle.py`: the only source file. It defines `RequestThrottle`
  with:
  - `mark_request(client_id)` -- records `self._clock()` as the last-seen
    time for a client.
  - `is_throttled(client_id)` -- computes `elapsed = self._clock() -
    self._last_seen[client_id]` and returns `elapsed < self.window_seconds`.
  - The class docstring states: "Blocks a client from repeating a request
    until the cooldown window has fully elapsed."
  - `_clock` defaults to a stub but is injectable, which makes deterministic
    testing of timing straightforward.

## What I concluded

The `is_throttled` check uses a strict `<` comparison: `elapsed <
window_seconds`. This means that the instant `elapsed` reaches exactly
`window_seconds` (the boundary of the cooldown window), the method already
reports "not throttled" and lets the client through. Per the class
docstring ("blocks ... until the cooldown window has fully elapsed") and the
report's own wording ("should have still been blocked for another moment"),
the client should still be considered blocked at that exact boundary
instant -- only once elapsed time moves *past* the window should the client
be let through. Because real clocks rarely land on the exact boundary tick
when a human is manually testing by waiting and retrying, this lines up with
the report's description of the issue being intermittent and hard to
reproduce by hand, while still happening in practice (e.g. under a fake/
deterministic clock, or when real timing coincidentally lands exactly on the
window edge).

I wrote `candidate_test.py` with an injectable fake clock that returns `0`
on the first call (used by `mark_request`) and exactly `10` (equal to
`window_seconds=10`) on the second call (used by `is_throttled`). This
deterministically simulates the "exactly at the edge of the cooldown
window" scenario described in the report, without relying on real wall-clock
timing or retries.

## What happened when I ran the test

I temporarily copied `candidate_test.py` into `buggy/`, ran `python -m
pytest candidate_test.py -v` from inside `buggy/`, and observed:

```
candidate_test.py::test_client_still_blocked_exactly_at_window_boundary FAILED

>       assert throttle.is_throttled("client-1") is True
E       AssertionError: assert False is True
```

The test failed with `AssertionError: assert False is True` -- confirming
that `is_throttled` returns `False` (not blocked) exactly at the cooldown
boundary, reproducing the bug described in the report. I then deleted the
temporary copy of `candidate_test.py` and the `__pycache__` / `.pytest_cache`
directories generated by the run from `buggy/`, leaving `buggy/throttle.py`
byte-for-byte unchanged. The real `candidate_test.py` remains only in the
working directory (sibling of `report.md` and `buggy/`).
