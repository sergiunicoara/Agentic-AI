# Trajectory

## What changed and why

The prior candidate asserted `len(result) == 1` as a bare literal. The
evidence check flagged this: the numeral `1` was not a verbatim quote from
`report.md` / `buggy/contacts.py`, not a literal constant appearing in the
test's own setup, and not tied to any accepted arithmetic derivation (the
prior BASIS operand `2.0` was disconnected from both the setup and the
quoted text). The second assertion (`result[0]["email"] ==
"jane.doe@example.com"`) was already grounded and did not need to change.

Fix applied: replaced the bare literal `1` with a value computed directly
from the test's own setup data, without calling the function under test:

```python
expected_unique_count = len({entry["email"].lower() for entry in entries})
```

Both `entries[0]["email"]` (`"jane.doe@example.com"`) and
`entries[1]["email"]` (`"Jane.Doe@example.com"`) are literal constants
written in the test's own setup. Lower-casing and set-deduplicating them is
plain, re-computable Python arithmetic over those two literals (it never
imports or invokes `unique_emails`), and it evaluates to `1`. The rule that
licenses treating the two case-variant strings as *the same* email — rather
than two independent kept entries — is quoted directly from report.md:
"[s]ame person, same email address, just typed with different
capitalization" and "catch that and only keep one of them" (see EVIDENCE
below for the exact literal offsets). So `expected_unique_count` is now a
derived value (KIND: derived), not an invented literal, and
`assert len(result) == expected_unique_count` inherits that grounding.

The email-identity assertion (`result[0]["email"] ==
"jane.doe@example.com"`) is unchanged and stays grounded the same way as
before: `"jane.doe@example.com"` is a literal constant from the test's own
setup (`entries[0]["email"]`), and `buggy/contacts.py`'s own docstring
states the function returns entries "keeping the first occurrence" — a
verbatim quote from a named buggy/*.py file. Since `entries[0]`'s email is
never removed ahead of itself, the surviving first element's email must
equal that literal.

No change was needed to the test's control flow / logic: the execution
evidence from the harness ("1 failing testcase(s) observed on buggy/")
already showed the test failing against `buggy/contacts.py` for the right
reason (case-sensitive `in` check on a `set` never treats
`"jane.doe@example.com"` and `"Jane.Doe@example.com"` as equal, so both
entries are kept and `len(result) == 2`). The problem was purely about
grounding the expected literal, not about the test not actually exercising
the bug.
